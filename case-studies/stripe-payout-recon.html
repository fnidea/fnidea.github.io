Case study

Three rebuilds of one weekly reconciliation

The work described here is at TixTrack, where I'm a senior financial analyst.

Before any of this, the weekly Stripe reconciliation took me 4 to 6 hours every week, and longer at month end.

Every client gets paid on its own week. Some run Monday to Sunday and some run Sunday to Saturday, and they're spread across five timezones, so every transaction has to land in the right client's week before anything gets booked. That's hundreds of thousands of lines in a single week.

First I'd download the reports from the Stripe website, and they were huge, so that alone took a long time.

The CSVs were too big to fully load in Excel, so I loaded them into Tableau workbooks to transform and filter them. That's where the client timezone matching lived at first, as a calculated field.

Then I'd export from Tableau to Excel as separate reports, and a consolidated workbook pulled them all together with Power Query.

Then the double-checks. Did I filter the dates right, and did every tab pull and update? There were more than 10 tabs, and that's my count from memory.

The KNIME version

I rebuilt it in KNIME first. It took about two months, and that's my guess, not something I tracked. But testing took longer than building.

I ran the new version side by side with the manual one and compared them line by line. When they didn't match I had to figure out which one was wrong. Sometimes it was the new one, and sometimes the manual process had been wrong for months and nobody noticed.

The queries pull one extra day on each side of the week, then a filter trims every row back to its own client's week. That replaced the timezone logic from the Tableau and spreadsheet days.

Rows that belong to a client get cut on the client's local day. Rows that don't belong to any client get cut on UTC. I went back and checked all 12 UK queries to make sure I actually did that, and it was 6 and 6.

I also moved client attribution out of the spreadsheet formulas and into the query, and I later collapsed nine categorization queries into one.

There's one branch whose only job is to catch any fee that doesn't fit the nine categories I already knew about. My note on it says "in case any additional fees pop up." It caught the per-auth fee, which the summary had been leaving out, and I fixed it so it flows through now.

Another workflow builds the NetSuite journal entry import. Debits and credits come from splitting each amount by its sign, and every line has an External ID, so if the import runs twice NetSuite updates it instead of booking it twice.

Once it's started it runs in 5 to 15 minutes. Door to door, with the typing and the review, it's under 30 minutes against the 4 to 6 hours it replaced.

What KNIME couldn't do

It only runs on my machine, because the file paths point at my desktop and a shared drive.

A re-run overwrites whatever was booked, so there's no way to see what we booked, what Stripe says now and what moved in between.

Every run starts with 10 parameters typed in by hand, dates and timezones included, and nothing checks them.

The US workflow has 10 copies of the same component, so one change means 10 edits. And all 12 of its database nodes are flagged deprecated by the vendor.

I also found that a reconciliation query's activity window was too narrow, and it had been missing backdated payment entries since January, about $110K of them.

And the find drove a reclassification at month-end close. I built a true-up view for costs and credits that show up once a week has been booked, and that's what surfaced those entries.

The console

So I rebuilt it again, as a Python console. It pulls the week's Stripe costs from Snowflake, runs them through an engine and writes the NetSuite import files. Each run builds two journal entries, one per payout window, plus a payments import.

I didn't write the code myself. Claude wrote it. My part is deciding what it has to produce and checking the output against the source data.

It checks 16 things before it lets me export, like every fee being categorized, the journal entries balancing, cost reconciling back to the source, and nothing being accrued twice.

On the week ending September 20, 14 checks passed, 1 warned and 1 got overridden. When I override a check, the reason gets written into the run log right next to the numbers it excused.

Every run saves the exact data it used with a fingerprint, so I can replay any week later even though Snowflake keeps changing. The KNIME version never kept anything, so this is the snapshot I'd designed to replace it, finally built.

It also checks every row against earlier runs by Stripe's own row ID. For the week ending September 20 that was 228,255 new rows and none that had been accrued before.

Rebuilding the journal entries from that saved snapshot matched 14 of 16 client groups to the cent. The other two were a $0.03 fee with no account mapped and $0.01 of rounding.

Each run writes six files: the journal entry import, the payments import, a summary workbook, a workpaper, the run log and the snapshot.

It's still in testing, running next to the manual process, and the week ending September 20 matches what was booked.

Running next to the manual process, the console exposed an error in one week's booked entry. Hand-typed date windows had given each week range an extra day that was already booked. I flagged it and it got fixed.

What it still can't do

It isn't posting yet. It's still being tested against the manual process.

An override records why I let a check through, but it doesn't fix anything. A fee I overrode with a note to map it stayed unmapped and unbooked, and that check will fail every week until I add the mapping.

Stripe doesn't send all of its fee data into Snowflake, so some fees can't be tied to a client. The console posts those to the platform line with no client name and warns me instead of guessing.

Posting straight into NetSuite isn't built. So it writes import files and a person still imports them.

What's next

The Stripe cost dashboard I built alongside it is supposed to replace the per-client workbooks, but they haven't been retired yet.

It surfaced a per-authorization fee the previous workflow had never pulled or booked. I fixed the dashboard's fee handling, and the fee gets booked going forward now.

Posting straight into NetSuite is the later phase for the console.
